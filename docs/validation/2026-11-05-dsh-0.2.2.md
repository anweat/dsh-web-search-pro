# 2026-11-05 验证：DSH 0.2.2-rc.1（dsh-web-search-pro 0.2.3）

结论：插件要适配 0.2.2 线，除 peer 之外必须改两处代码：读配置的位置（`fiber.effectiveConfig`），以及设置卡片私有 RPC 通道的挂载（0.2.2-rc.1 的 `connection.rpc.handle()` 对外部插件抛错，插件改走宿主的 `register(owner, …)` 回退）。两处修好后，`0.2.0-rc.2`、`0.2.1-rc.5`、`0.2.2-rc.1` 三个真实宿主上的各项都通过。`0.2.2` 正式版靠 `0.2.2-rc.1` 的这轮验证放行，没有另对正式版做验证。

**2026-11-09 更新**：通道挂载已从“`handle` 失败回退到宿主私有的 `register`”改为经派生上下文调用公开的 `rpc.handle`，不再依赖宿主私有方法，三个宿主已重验，见文末“2026-11-09”一节；下文第 5 节的“通道回退”是 2026-11-05 当时的做法，保留作为记录。

## 2. PR #44 的 `?? {}` 与最终版的差异（0.2.2-rc.1，同一份探针）

| 构建 | A 无配置 | B 配置含表达式 | C 普通值部分配置 | D 表达式 `timeoutMs` |
|---|---|---|---|---|
| `peeronly`（`resolveConfig(ctx.fiber.config)`） | **entry 不激活**（`web_call` 缺席） | **不激活** | 通过 | 未测 |
| `pr44`（`?? {}`） | 通过 | **不激活**：`TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received an instance of Object`（栈在 `resolveConfig` ← `baseline` ← `SearchRouter` 构造），宿主只报 `warning: 1 entry did not activate` | 通过 | 激活，但 `config.inspect` 与 `sources.status` 持续报“⚠ 待重启：timeoutMs（当前生效 45000，配置为 [object Object]）” |
| `final`（`effectiveConfig ?? config ?? {}`） | 通过 | 通过 | 通过 | 通过，无误报 |

要点，和 PR #44 的说法对照：

- PR #44 说“`?? {}` 修了没有配置的 entry”：成立（A 通过）。
- 它没说、也没验证的：raw `fiber.config` 里的表达式不求值。配置含 `!!js` 的 entry 在 `?? {}` 版本上要么启动失败（表达式落在 `dbPath` 这类会被立刻用到的字段上），要么 `pendingRestart` 误报。这是 `effectiveConfig` 修法与 `?? {}` 的可观察差别。
- brief 里预期的“只写部分字段时 schema 默认值被跳过（包括嵌套字段）”：**这一点在本插件上没有观察到差别**。`resolveConfig()` 自己对每个字段都有缺省值（含 `evidence`、`sources`、`provider`），所以 C 用例里原样的 `ctx.fiber.config` 与 `?? {}` 与 `effectiveConfig` 结果相同（`evidence.maxRounds=5`、`scorer=rule` 等一致）。凭据引用也是同样：`exaApiKeyEnv` 是环境变量名，路由器每次调用经 `ctx.credentials.resolve` 解析，与读哪个对象无关，C 用例三种构建都是 `credential=configured`。
- 所以 `effectiveConfig` 的必要性来自表达式（以及将来任何 `internal/config` 钩子的结果），而不是缺省值。

**根因（0.2.2-rc.1 宿主侧）**：插件用 `ctx.inject(['connection', 'webServer'], c => c.effect(() => c.connection.rpc.handle(CHANNEL, handler)))` 注册通道（`src/rpc.ts`；与 dsh-browser 的 `automation-assets-rpc.ts` 同一写法）。回调触发了，但 `connection.rpc.handle()` 抛 `Error: cannot get property "webServer" without inject`，栈在 `dsh-client-connection/lib/index.js` 的 `register()` 里 `owner.effect(() => owner.webServer.register(route))`。cordis 4.1 的 `reflect` 现在按**定义处**（`ctx[symbols.shadow]`）检查 `inject` 声明：`register` 是 `dsh-client-connection` 的方法，它的定义处是 Connection 插件自己的上下文，而那个上下文只声明了 `inject = ['credentials']`，没有 `webServer`。我在已安装副本里试过三种写法（`connectionCtx.root.connection`、`connectionCtx.connection`、在 effect 内外调用），都得到同一个错误，`connectionCtx.webServer` 本身可以读到。宿主自己的测试在根上下文（无 fiber）里调用 `rpc.handle`，检查被绕过，所以没暴露。异常发生在 effect 里，没有出现在日志中，现象只是通道没挂上、浏览器得到 405。当时我判断插件侧没有绕过，这个判断不对：见下一节，`register` 方法虽然在宿主的类型里是 private，运行时可用。

### 通道回退（`src/rpc.ts` 的 `openChannel`）

做法（与 dsh-browser 的 b962550 同一思路）：先试 `connection.rpc.handle(channel, handler)`；它抛错时，改调宿主 `HostConnectionService.register(owner, channel, handler)`，`owner` 传注入了 `webServer` 的那个上下文（`connectionCtx`）。`register` 在宿主类型里是 TypeScript-private，运行时存在，所以**这条回退依赖宿主的一个私有方法**；若某个宿主版本去掉了它，`registerRpc` 在 effect 里捕获 `openChannel` 的任何失败（`handle` 与 `register` 都失败、或 `register` 自己抛错），用 `console.warn` 打一行（频道名、原因、卡片仍渲染但实时状态 / agent 修改面板 / CLI 试运行不可用），返回空的卸载函数，插件照常运行（宿主不报告 inject 回调里的抛错，`ctx.logger` 在默认级别会丢掉这类 warn，所以用 console）。在 0.2.2-rc.1 的已安装副本里强制 `register` 不可用实测：服务日志出现 `web-search-pro: settings-card RPC channel /dsh-web-search-pro was not mounted (cannot get property "webServer" without inject); the card still renders, but its live status, agent-edits panel and custom-CLI dry-run will not work`，卡片渲染、改一项保存、恢复仍正常（`fallback/no-register/`，卡片的私有请求按预期 405）。上游根因：`packages/client/connection/src/rpc-host.ts` 的 `register()` 里 `owner.webServer`，在 cordis 4.1 的“按定义处检查 inject”下抛错；宿主自己的测试跑在根上下文，检查被绕过。

单元测试 `test/rpc-channel.test.ts` 固定：`handle` 可用（不碰 `register`）、`handle` 抛错且有 `register`（拿到注入上下文、频道与 handler）、`handle` 抛错且没有 `register`（原错误抛出）、`register` 自己抛错（其错误抛出），以及告警行的内容（含频道名与原因、无 ANSI）。
