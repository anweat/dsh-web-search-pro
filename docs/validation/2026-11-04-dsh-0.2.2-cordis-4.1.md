# 验证记录：DSH 0.2.2-rc.1（cordis 4.1）兼容性

日期：2026-11-04。执行者：贡献者侧代理（非独立验证者）。只写亲眼看到的结果。

## 被测对象与环境

- 插件：分支 `fix/dsh-0.2.2-cordis-4.1`（基于 upstream `8b6e5c6`，即 0.2.3 + 文档整理）；`tar` 打出 tgz（内容与 `files` 一致），以 `file:` 安装，和 npm 用户一样走宿主的安装闸门。
- 宿主：从 npm 官方源装进工作区内的隔离目录（不碰任何现有环境的宿主、不读写 `~/.dsh`）：`@deepseek-ai/dsh` **0.2.0-rc.2**、**0.2.1-rc.2**、**0.2.2-rc.1**。三者干净安装后的顶层 cordis 分别是 **4.0.4**、**4.0.5**、**4.1.0**（与各自 `dsh-app-boot` 的 peer 一致）。
- 隔离：每次测试用全新的 `DSH_HOME`；端口用 1896x，不占用 3080；不读凭据文件，不跑真实模型。
- 驱动：`test/compat/` 下的脚本化 mock 模型（只说够宿主跑完一次工具调用的 OpenAI 协议），headless 跑一个回合，要求模型调用 `web_call`（`action: cache.stats`），并**断言拿到 `status: completed` 的 `tool_result`**。

> 说明：判定条件必须是 completed 的 tool_result，不能只看 `tool_call` 事件。模型点名一个不存在的工具时宿主照样返回 `{"type":"tool_call"}`，随后才给 `Error: unknown tool`，只看前者会把"插件根本没注册工具"判成通过。本次排查正是先踩到这个坑。

## 一、发现的问题

在 `0.2.2-rc.1` 上，未改动的 0.2.3 表现为：宿主只打印一行 `warning: 1 entry did not activate`，所有工具缺席，headless 回合得到 `Error: unknown tool "web_call"`。

宿主的原文（完整栈）：

```
web-search-pro (dsh-web-search-pro): TypeError: Cannot read properties of undefined (reading 'dbPath')
    at resolveConfig (.../dsh-web-search-pro/lib/config.js:187:31)
    at Object.baseline (.../dsh-web-search-pro/lib/index.js:74:28)
    at OverlayStore.effective (.../overlay.js:391:35)
    at SearchRouter.dynamic (.../index.js:85:35)
    ...
```

根因在 cordis 的次版本变更，用一个最小探针直接对照得到（同一个插件对象、不传 config、只读 `ctx.fiber.config`）：

| cordis | `ctx.fiber.config` |
|---|---|
| 4.0.5（0.2.0 / 0.2.1 线） | `{"dbPath":"/tmp/x.db"}` —— **没传 config 也套了一边 schema 默认值** |
| 4.1.0（0.2.2 线） | `undefined` |

`baseline()` 把这个值原样交给 `resolveConfig()`，后者第一行就是 `config.dbPath`，因此 `undefined` 直接抛错，整条 entry 挂不上。

## 二、修复

`resolveConfig((ctx.fiber.config ?? {}) as Config)`：空对象走 `resolveConfig` 自带的默认值分支（每个字段都有 `vOr` 兜底），两代 cordis 得到相同的 ResolvedConfig。

## 三、真实宿主结果

| 宿主 | cordis | 修复前 | 修复后 |
|---|---|---|---|
| 0.2.0-rc.2 | 4.0.4 | 通过 | **通过** |
| 0.2.1-rc.2 | 4.0.5 | 通过 | **通过** |
| 0.2.2-rc.1 | 4.1.0 | **失败**（entry 不激活） | **通过** |

三次运行都拿到 completed 的 `tool_result`，内容是插件自己 `cache.stats` 的输出（库路径、大小、计数），说明插件确实挂上了、工具确实执行了。

## 四、接口核对

插件从宿主导入的符号，在 `0.2.1-rc.5` 与 `0.2.2-rc.1` 的包内逐个查找，全部存在：`defineTool`（dsh-tools）、`credentialRef`（dsh-credentials）、`SnapshotStore`（dsh-client-store）、`PropsLocale`（dsh-client-ui-slots）、`Button` / `Modal` / `Switch` / `Tag` / `Tooltip`（dsh-client-ui-primitives）。`Context`（cordis）与 schemastery 的用法未变。

`0.2.1-rc.5`（当前生产的宿主）只做了两件事：production profile 的 `--dump-config` 退出码 0、无 `did not activate`；以及确认它带的 cordis 是 4.0.5、落在新的 `~4.0.4 || ~4.1.0` 内。**没有**在 rc.5 上跑 headless 回合。

## 五、peer 范围检查

`node test/compat/check-peer-ranges.js`（含 `--selftest`，本次把自检从 25 条扩到 32 条）：三段范围对 6 个受支持基线（0.2.0-rc.2、0.2.1-rc.2 ~ rc.5、0.2.2-rc.1）runtime 与 install 两种模式均通过；0.1.7-rc.2、0.2.0-rc.1、0.2.1-alpha.5、0.2.1-rc.1、0.2.2-alpha.1、0.2.3-rc.1 均拒绝。cordis `~4.0.4 || ~4.1.0` 放行 4.0.4 / 4.0.5 / 4.1.x，拒绝 4.2.0 起。

## 六、局限

- 只验证了 headless（不带 Web 前端的设置卡片）。`0.2.2-rc.1` 的客户端面板没有在浏览器里看过。
- 没有跑登录类平台（xhs / zhihu / reddit / twitter），也没有跑真实模型会话。
- `0.2.1-rc.5` 未跑 headless 回合，见第四节。
- cordis 4.1 的这个行为变更只对照了 4.0.5 与 4.1.0 两个版本；4.1.x 中间版本未逐一取用。
