# 免登录 CLI 实测报告（2026-10-26）

范围：`dsh-web-search-pro` 的 CLI 适配层，对不需要登录态的工具做真实查询；登录类（xhs、zhihu、rdt、twitter、独立 opencli）只读 `--help`/`--version` 与源码，未运行任何搜索或登录命令。分支 `test/cli-live`（从未发布的 0.2.2 `119cbf6` 切出），所有结论来自本机实际输出；宿主侧证据在 `environments/websearch-cli-2026-10-26/`。

执行者是编写这些适配的同一代理，不是独立验证者。

## 结论一览

| CLI | 免登录？ | live 通过？ | 修了什么 |
|---|---|---|---|
| `bili` 0.6.2 | 是（`bili search` 路径不取凭据、不读浏览器 Cookie：`bili_cli/commands/user_search.py` → `client.search_video` 无 credential；浏览器提取只在 `auth.py` 的登录/需要登录的命令里） | 是（中/英/特殊字符） | 约五分之一的条目是没有 bvid/链接的课程/系列，请求 3 条只回 2 条（宿主会话里看到）：规格新增 `overfetch: 3`，count 现在能满足 |
| `gh` 2.101.0 | **不完全**：任何 `gh` 命令都需要它自己的登录（无 token 时直接提示 `gh auth login`，已用空 `GH_CONFIG_DIR` 验证）；不是浏览器 Cookie，用户已登录 anweat，只读搜索 | 是（repos 中/英/特殊/空、issues、code；issues 与 code 首次真实运行） | 查询作为一个参数交给 gh，gh 把它当精确短语：四词查询（`DeepSeek 搜索 插件 问题`）返回空、`repo:x 多个词` 是无效查询。新增 `{terms}`（按词拆参数、引号保持短语）。注意：插件默认链是 `rest → gh`，gh 只是回退 |
| `omnireach` 0.19.0-alpha | wechat 源是（Sogou，无 Key、无登录、无浏览器）；**多源命令原先不是** | 是（wechat：中/英/无结果；多源：中/英） | 见下“事件 1”：多源命令改为显式 `--on hackernews,youtube,github,wechat,bilibili`；见“事件 2”：NO_PROXY 的 `[::1]` |
| `yt-dlp` 2026.08.19 | 是 | 是（中/英/特殊/无结果/直播） | 直播没有播放量/时长，yt-dlp 打印 `NA`，规格只认 `None`，摘要变成 “NA views \| NA”；`emptyValues` 加 `NA`，时长改 `%(duration>%H:%M:%S)s`（`duration_string` 对 11 秒的视频只打印 “11”） |
| `wx-search-cli` 0.1.0 | 是（Sogou 自己下发的会话 Cookie，不读浏览器、不登录：`dist/weixin-search.js`） | 是（升级 contract-only → live；中/英/无结果） | 规格不需修改。记录两点行为：每页固定 10 条（适配层按 count 截取）；Sogou 反爬时输出 `[]` 且退出码 0，与“无结果”无法区分，只能报 `ENGINE_EMPTY` |
| `mcporter` 0.13.13 → Exa（keyless） | 是（`~/.mcporter/mcporter.json` 里 `exa` 是 `https://mcp.exa.ai/mcp`，无 Key；`EXA_API_KEY` 未设置） | 是（中/英/特殊/无意义查询，各 3 条） | 无需修改。它不是 CLI 规格而是 `exaEngine` 的回退路径，所以没有“规格状态”，只有夹具 `live-mcporter-exa-*.txt` 与离线解析测试 |

事件 1（omnireach 多源，最重要）：`omnireach search <q> --limit N --json` 不带 `--on` 时，omnireach 0.19 的 `augment_with_active_browser_sources` 会在 PATH 上有 `opencli`（或配置了 Chrome 桥）时自动追加 `google` 与 `twitter` 源，通过 `opencli` 驱动用户的 Chrome（实测 21.6 秒的中文查询里有 5 条 google + 5 条 twitter，adapter 都是 `opencli`；用替身 `opencli` 复现，被调用的是 `twitter search … --window background --site-session ephemeral --keep-tab false` 与 `google search …`）。原规格注释和 README 写的是“浏览器源在工具里是 opt-in 的”，这是错的。**我自己的前两次多源实测就触发了这个行为**（查询 “DeepSeek 联网搜索 插件” 与 “rust async runtime comparison”），也就是说那两次在你的 Chrome 里后台跑了只读的 google/twitter 搜索，用的是你 Chrome 里的会话（搜索词无害，没有任何写操作，但我当时没预料到）。已修：多源命令显式 `--on`，显式源不会被扩充；`test/cli-live.test.ts` 在 PATH 前面放一个会记录调用的替身 `opencli`，断言多源搜索从不调用它；改完之后宿主会话里 `ls` 替身目录确认没有任何意外调用。

事件 2（NO_PROXY，宿主里才暴露）：宿主会话 2 里 wechat 链的第一后端 omnireach 报 `Invalid port: ':1]'`，链回退到 wx-search-cli，而 `sources.status` 同时显示 omnireach `ready`。原因：宿主进程的 `NO_PROXY` 含 `[::1]`，omnireach 的 httpx 解析不了方括号 IPv6 条目，所有源失败。在普通终端用 `NO_PROXY="localhost,127.0.0.1,[::1]"` 可复现（`::1` 不带括号则正常）。`buildCliEnv` 现在把 NO_PROXY/no_proxy 里的 IPv6 条目写成不带方括号的形式（代理 URL 里的括号不动）。第 3 个宿主会话里用一个只记录环境的 omnireach 包装脚本确认：子进程收到的 `NO_PROXY=localhost,127.0.0.1,::1,.local,::1`（`evidence/omnireach-child-env.log`），搜索由 omnireach 完成。我没有打印宿主进程原始的 NO_PROXY，这个因果链是“复现 + 修复后好了”，不是直接读到宿主值。

## 做了什么、看到了什么

### 契约探测与查询

每个 CLI 都先用插件的 `probeCli`（只跑 `--version` 与 `search --help` 等规格里的探测命令）确认 `detected` 与版本，再用 `buildArgv` + `runCliSearchDetailed` 执行，同时用同样的 argv 再取一份原始输出对照（非 TTY）。查询：

- bili：`DeepSeek 本地部署教程`(5)、`rust async runtime tutorial`(3)、`C++ "template" <b>& 100%`(3)、无意义串、`-DeepSeek`(3)；bili 没有“无结果”（总有模糊匹配），无结果走构造夹具 `{"ok":true,"data":[]}`。
- gh：repos `DeepSeek 插件`、`web search plugin`、`-sort stars:>5 "quoted" & <x>`（修复后正确地返回空）、无意义串；issues `repo:anweat/dsh-web-search-pro is:issue twitter`、`DeepSeek 搜索 插件 问题`；code `web_call repo:anweat/dsh-web-search-pro`、无意义串。
- yt-dlp：`DeepSeek 本地部署教程`、`rust async runtime tokio`、`C++ "template" <b>& 100% | $x; \`id\``(shell 元字符，直接作为单个 argv，没有被解释)、`-DeepSeek`、无意义串、`lofi hip hop radio live 24/7`(直播)。
- wx-search-cli：`人工智能`、`DeepSeek V4 harness`、无意义串、`-"AI" & <b>100%`（空，可能是 Sogou 的结果也可能是反爬）。
- omnireach：wechat `大模型 备案` / `DeepSeek harness plugin` / 无意义串；多源 `DeepSeek 联网搜索 插件` / `rust async runtime comparison`。
- Exa：`rust async runtime comparison`、`DeepSeek 联网搜索 插件 对比`、`C++ "template" <b>& 100%`、无意义串（语义搜索永不为空）。

检查项：URL 是 http(s) 且形状正确、标题非空且不是字段名（#38 的症状）、没有 `NA`/`None`/`-` 占位文本、没有重复链接、条数 ≤ count、`publishedAt` 可解析。除上面列出的 gh / yt-dlp / bili / omnireach 缺陷外，其余通过。其他观察（未改）：

- bili JSON 没有发布时间，`publishedAt` 恒空；`duration` 是 bili 自己的 “4:4” 这类原样值。
- Exa（mcporter）的 `Published: N/A` 被丢弃；snippet 是整段 Markdown 高亮，被截到 400 字符并带 “(Content truncated at 400 characters.)” 尾注（所有 CLI 的 `capText` 都这样）。
- gh 的 `--sort stars/updated` 是规格的既有选择：对 repos 是“最热门”而非“最相关”，对 issues 是“最近更新”，不是最佳匹配。没改。
- omnireach 多源的 `--limit` 是“每个源”的上限，插件再按 omnireach 的排序取前 count 条；多源的 `errors` 在有结果时不报告（NO_PROXY 事件里别的源都挂了也看不出来）。没改。

### 后端链

用真实 PATH、隔离 store 的 `SearchRouter`（`allowProxyFakeIp: true`），登录类命令只会被探测（`--version`/`search --help`）；独立 opencli 用一个替身（只回放已捕获的 `opencli list` 夹具，任何其他调用都会写日志，日志始终为空），所以真实 `opencli list -f json` 也没有运行。

- 默认顺序与 `sources.status`：wechat 先 omnireach（`ready 0.19.0`）后 wx-search-cli（`ready 0.1.0`）；github / github-issues：`rest`（匿名）→ `gh`；github-code：`rest` 因“GitHub code search requires authentication”被跳过，gh `ready`，整体 `login_unverified`（“gh will use your own session, which cannot be checked locally”）——准确；bilibili / youtube 单后端 `ready`。
- 配置顺序：`platformBackends.wechat = [wx-search-cli, omnireach]` 后，历史记录里服务者是 `wx-search-cli`；默认时是 `omnireach`。
- 回退：把 omnireach 从 PATH 拿掉，wechat 由 wx-search-cli 回答，历史/说明为 `skipped backends: omnireach: …`。**这里发现并修了一处**：原来只写 `omnireach: unavailable`，现在引擎可提供 `unavailableReason()`，说明变成 “the omnireach command is not installed: install it (…)”。github 用一个无效 token 让 REST 返回 401，链回退到 gh，说明为 `skipped backends: github: GitHub API 401 (token rejected or rate-limited)`。
- 登录类后端在没有登录文件时：用空 HOME 和真实 HOME 各查一遍（真实 HOME 里 xhs/zhihu/rdt 的登录文件都不存在）。xhs / rdt / zhihu：`[skipped] … cred=missing — xhs: no saved login (run \`xhs login\` yourself)`（rdt、zhihu 同形）；twitter：`TWITTER_AUTH_TOKEN / TWITTER_CT0 not set (…DSH credentials (plugin settings twitterAuthToken / twitterCt0) or in the Host process environment; a shell profile alone is not enough)`；xiaohongshu / reddit / twitter 的标准 opencli 后端显示 `ready`、整体 `login_unverified`（“opencli will use your own session, which cannot be checked locally”）；zhihu 在没有 dsh-browser 时整体 `needs_login`。这些文案与实际状态相符。一处不够细：`sources.status` 的 xhs / rdt 跳过原因没有说明“没有登录文件时该工具会自己读浏览器 Cookie，所以不运行”（这句话只在运行时错误里出现），可以补，没做。
- 这些检查中没有运行任何登录类命令的搜索或登录。
